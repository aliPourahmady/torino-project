## ‏۲. مدیریت state سراسری

‏**پاسخ: بله، ولی بسیار کوچک.** بخش بزرگ state این پروژه «server state» است (تورها، پروفایل، تراکنش‌ها) و جایش React Query است، نه یک store سراسری. تنها چیزی که واقعاً سراسری و مربوط به UI است، **مودال ورود** است:

- ‏مودال ورود از چند جا باز می‌شود: دکمه‌ی «ورود | ثبت نام» در هدر، دکمه‌ی رزرو در صفحه‌ی تور (اگر کاربر وارد نشده باشد) و ریدایرکت middleware برای صفحات محافظت‌شده.
- ‏مودال دو مرحله دارد (شماره موبایل ← کد تایید) و شماره‌ی موبایل مرحله‌ی اول باید در مرحله‌ی دوم هم در دسترس باشد.
- ‏بعد از ورود موفق باید کاربر به همان کاری که می‌خواست انجام دهد برگردد (مثلاً ادامه‌ی خرید).

‏**store پیشنهادی (Redux Toolkit):** یک slice به نام `authModal`:

```js
// store/authModalSlice.js
import { createSlice } from '@reduxjs/toolkit'

const authModalSlice = createSlice({
  name: 'authModal',
  initialState: {
    isOpen: false,
    step: 'mobile', // "mobile" | "otp"
    mobile: '',
    redirectAfterLogin: null,
  },
  reducers: {
    openModal(state, action) {
      state.isOpen = true
      state.step = 'mobile'
      state.redirectAfterLogin = action.payload?.redirectTo ?? null
    },
    closeModal(state) {
      state.isOpen = false
      state.mobile = ''
    },
    setStep(state, action) {
      state.step = action.payload
    },
    setMobile(state, action) {
      state.mobile = action.payload
    },
  },
})

export const { openModal, closeModal, setStep, setMobile } =
  authModalSlice.actions
export default authModalSlice.reducer
```

‏**چرا Redux Toolkit و نه Context؟** با `useSelector` هر کامپوننت فقط به بخشی از state که لازم دارد گوش می‌دهد؛ در Context با تغییر مقدار، همه‌ی مصرف‌کننده‌ها دوباره رندر می‌شوند. `createSlice` منطق تغییر state را در یک فایل نگه می‌دارد و Redux DevTools باز و بسته‌شدن مودال و تغییر مرحله را قابل ردیابی می‌کند.

‏**نکته‌ی Next.js:** `Provider` ریداکس باید داخل یک Client Component (با `"use client"`) باشد. آن را در `components/providers/Providers.js` می‌سازم و در `layout.js` ریشه دور `children` می‌گذارم. چون این store فقط state رابط کاربری دارد، رندر سروری صفحات (SSR و ISR) تحت تاثیر قرار نمی‌گیرد.

‏**چیزهایی که عمداً داخل store نمی‌گذارم:**

- ‏اطلاعات کاربر (نام، موبایل): با `useProfile()` در React Query نگه داشته می‌شود تا بعد از ویرایش پروفایل با `invalidateQueries` خودکار به‌روز شود.
- ‏توکن‌ها: در کوکی `httpOnly` ذخیره می‌شوند (بخش ۴ و ۵).
- ‏سبد خرید: روی سرور API نگه‌داری می‌شود (`GET /basket`)، پس منبع حقیقت سرور است.

## ‏۳. صفحات و روش رندر

‏بر اساس فیگما، **۶ مسیر اصلی** و **۲ صفحه‌ی خاص** (۴۰۴ و خطا) داریم. ورود یک مودال است، نه صفحه. ویرایش پروفایل هم به‌صورت حالت ویرایش داخل صفحه‌ی پروفایل طراحی شده، نه مسیر جدا.

| ‏#  | ‏صفحه                             | ‏مسیر                    | ‏روش رندر                                            | ‏دلیل                                                                                                                                                                                                                                         |
| --- | --------------------------------- | ------------------------ | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ‏۱  | ‏صفحه‌ی اصلی (جستجو و لیست تورها) | ‏`/`                     | ‏**SSR با کش داده‌ی `fetch`** (`revalidate: 60`)     | ‏فیلترها (مبدا، مقصد، تاریخ) در URL و با `searchParams` می‌آیند و لینک نتایج قابل اشتراک است. خواندن `searchParams` صفحه را dynamic می‌کند، ولی کش داده‌ی `fetch` از درخواست‌های تکراری به API جلوگیری می‌کند. محتوای تورها برای SEO مهم است. |
| ‏۲  | ‏جزئیات تور                       | ‏`/tours/[tourId]`       | ‏**ISR** (`generateStaticParams` + `revalidate: 60`) | ‏محتوا کم‌تغییر و عمومی است. فقط `availableSeats` بعد از خرید عوض می‌شود. تا ۶۰ ثانیه تاخیر قابل‌قبول است، چون ظرفیت نهایی هنگام ثبت سفارش در سرور بررسی می‌شود.                                                                              |
| ‏۳  | ‏ثبت و خرید نهایی                 | ‏`/checkout`             | ‏**CSR**                                             | ‏به کاربر و سبد خرید او وابسته است، قابل کش عمومی نیست و SEO ندارد.                                                                                                                                                                           |
| ‏۴  | ‏پروفایل                          | ‏`/profile`              | ‏**CSR** (layout سرور، محتوا کلاینت)                 | ‏داده‌ی خصوصی و تعاملی (ویرایش).                                                                                                                                                                                                              |
| ‏۵  | ‏تورهای من                        | ‏`/profile/my-tours`     | ‏**CSR**                                             | ‏داده‌ی خصوصی.                                                                                                                                                                                                                                |
| ‏۶  | ‏تراکنش‌ها                        | ‏`/profile/transactions` | ‏**CSR**                                             | ‏داده‌ی خصوصی.                                                                                                                                                                                                                                |
| ‏۷  | ‏صفحه‌ی ۴۰۴                       | ‏`not-found.js`          | ‏**SSG**                                             | ‏کاملاً ایستاست.                                                                                                                                                                                                                              |
| ‏۸  | ‏صفحه‌ی خطای اتصال                | ‏`error.js`              | ‏**CSR** (الزاماً Client Component)                  | ‏Next.js error boundary را باید کلاینتی بسازد و دکمه‌ی «تلاش مجدد» با `reset()` کار می‌کند.                                                                                                                                                   |

‏**نکته‌ی fetch و axios:** کش و `revalidate` قابلیتی مخصوص `fetch` در Next.js است و درخواست‌های `axios` در آن شرکت نمی‌کنند. بنابراین در Server Componentها (صفحه‌ی اصلی و جزئیات تور) از `fetch` استفاده می‌کنم و `axios` فقط سمت کلاینت (همراه React Query) به کار می‌رود. از Next.js نسخه‌ی ۱۵ به بعد `fetch` به‌طور پیش‌فرض کش نمی‌شود، پس `next: { revalidate: 60 }` را باید صریح بنویسم.

‏**نکته‌ی مهم درباره‌ی ترکیب ISR و احراز هویت:** اگر هدر در سرور کوکی را بخواند (`cookies()`)، تمام صفحات dynamic می‌شوند و ISR صفحه‌ی تور از بین می‌رود. به همین دلیل وضعیت ورود در هدر را **سمت کلاینت** با `useProfile()` تشخیص می‌دهم. صفحات عمومی ایستا یا ISR می‌مانند و فقط جزیره‌ی کوچک هدر کلاینتی است. تا زمانی که پروفایل در حال بارگذاری است، یک اسکلت نمایش می‌دهم.

## ‏۴. ساختار پروژه

### ‏تصمیم‌ها و دلیل‌ها

- ‏**همه‌چیز زیر `src/`**: کد برنامه از فایل‌های پیکربندی ریشه جدا می‌شود و ساختار تمیزتری دارد.
- ‏**هدر و فوتر در `layout.js` ریشه**: در فیگما حتی صفحات ۴۰۴ و خطا هدر و فوتر کامل دارند. `not-found.js` فقط داخل layout ریشه رندر می‌شود، پس هدر و فوتر باید همان‌جا باشند.
- ‏**دو route group**: `(public)` برای صفحات عمومی و `(private)` برای صفحاتی که ورود می‌خواهند. این گروه‌بندی URL را تغییر نمی‌دهد و فقط خوانایی می‌آورد. حفاظت واقعی در `middleware.js` است (matcher روی `/checkout` و `/profile/*`).
- ‏**لایه‌ی `services/`** جدا از کامپوننت‌ها: هر endpoint یک تابع دارد. اگر آدرس یا شکل پاسخ API عوض شود، فقط یک جا تغییر می‌کند.
- ‏**پوشه‌ی `validations/`**: schemaهای `yup` (ورود، مسافر، پروفایل) از کامپوننت‌ها جدا و قابل استفاده‌ی مجدد هستند.
- ‏**`app/api/`** به‌عنوان لایه‌ی واسط (BFF سبک): توکن‌ها در کوکی `httpOnly` می‌مانند تا با حمله‌ی XSS قابل سرقت نباشند. Route Handlerها توکن را به درخواست‌های محافظت‌شده اضافه می‌کنند و رفرش توکن را در یک نقطه انجام می‌دهند.
- ‏**`components/` بر اساس دامنه** (auth، tours، checkout، profile) به‌علاوه‌ی `ui/` برای کامپوننت‌های عمومی بدون منطق کسب‌وکار. هر کامپوننت فایل `.module.css` خودش را کنار خودش دارد.

## ‏۵. بخش‌های چالش‌برانگیز

‏**۱. احراز هویت و رفرش توکن**

‏توکن دسترسی (`accessToken`) یک ساعت و توکن رفرش (`refreshToken`) هفت روز اعتبار دارد. در کد API چند نکته‌ی ظریف وجود دارد:

- ‏اگر توکن نامعتبر باشد، API با کد وضعیت `403` پاسخ می‌دهد.
- ‏اگر توکن اصلاً ارسال نشود، کد وضعیت `401` است.

‏بنابراین منطق رفرش باید هر دو حالت را پوشش دهد. همچنین وقتی چند درخواست هم‌زمان با توکن منقضی ارسال شوند، فقط یک رفرش باید انجام شود و بقیه‌ی درخواست‌ها منتظر نتیجه‌ی آن بمانند؛ در غیر این صورت چند رفرش موازی اجرا می‌شود. این منطق را در `api/proxy` متمرکز می‌کنم.

‏**۲. تقویم شمسی و فیلتر تاریخ**

‏تقویم طراحی‌شده شمسی است، ولی API تاریخ‌ها را میلادی (ISO) می‌گیرد و برمی‌گرداند. هم تبدیل رفت‌وبرگشتی باید دقیق باشد و هم معنای فیلتر روشن شود: API تورهایی را برمی‌گرداند که تاریخ شروعشان بزرگ‌تر یا مساوی `startDate` و تاریخ پایانشان کوچک‌تر یا مساوی `endDate` باشد.

‏**۳. فرم جستجو بدون endpoint شهرها**

‏API فقط `originId` و `destinationId` را فیلتر می‌کند، ولی endpoint‌ای برای دریافت **فهرست شهرها** ندارد. گزینه‌های dropdown باید از روی تورها استخراج یا ثابت تعریف شوند. نام شهرها هم در API انگلیسی است (مثلاً `Tehran`) و باید به فارسی نگاشت شود.

‏**۴. جریان سبد خرید و ثبت سفارش**

‏مسیر خرید سه مرحله دارد:

- ‏`PUT /basket/:tourId` برای افزودن تور به سبد
- ‏`GET /basket` برای خواندن سبد در صفحه‌ی checkout
- ‏`POST /order` برای ثبت سفارش

‏نکات کد API که باید با آن‌ها کار کرد:

- ‏سبد خرید در یک فایل واحد (`Basket.json`) ذخیره می‌شود، نه به‌ازای هر کاربر. پس در تست با چند کاربر، سبد مشترک است.
- ‏`POST /order` شناسه‌ی تور را از سبد می‌خواند (نه از body) و فقط `nationalCode`، `fullName`، `gender` و `birthDate` را می‌گیرد؛ یعنی هر سفارش **یک مسافر** است.
- ‏بعد از خرید موفق سبد خالی می‌شود و صفحه‌ی checkout با سبد خالی باید کاربر را به جای مناسب هدایت کند (API با کد وضعیت `404` و پیام «سبد خرید شما خالی است» پاسخ می‌دهد).

‏**۵. تازگی داده و کش**

‏بعد از خرید، ظرفیت تور کم می‌شود ولی صفحه‌ی ISR تا ۶۰ ثانیه قدیمی می‌ماند. باید تصمیم بگیرم که این تاخیر قابل‌قبول است یا با `revalidateTag` پس از خرید (از طریق Route Handler) کش را فوراً باطل کنم.

‏**۸. حالت‌های ناقص در طراحی**

‏حالت‌های loading، خالی (تور پیدا نشد، تراکنشی وجود ندارد) و خطای فرم در فیگما دیده نمی‌شوند و باید خودم بر اساس سیستم طراحی آن ها را بسازم .

## ‏۷. جمع‌بندی

- ‏**نوع پروژه:** سایت رزرو تور با ۶ مسیر اصلی، مودال ورود دومرحله‌ای (OTP) و دو صفحه‌ی خطا. بیشتر پیچیدگی در **احراز هویت، جریان خرید و هماهنگی UI با API** است، نه در خود صفحات.
- ‏**معماری رندر:** صفحات عمومی (اصلی، جزئیات تور) سمت سرور با کش (SSR/ISR) برای سرعت و SEO؛ صفحات خصوصی (checkout، پروفایل) کلاینتی با React Query.
- ‏**دریافت داده:** `fetch` در Server Componentها (برای استفاده از کش Next.js) و `axios` سمت کلاینت همراه React Query.
- ‏**state:** React Query برای server state و یک slice کوچک Redux Toolkit فقط برای مودال ورود.
- ‏**امنیت:** توکن‌ها در کوکی `httpOnly` و رفرش در یک نقطه‌ی مرکزی (`api/proxy`)؛ وضعیت ورود در هدر سمت کلاینت تا ISR صفحات عمومی حفظ شود.
- ‏**UI:** حدود ۱۶ الگوی تکراری شناسایی شد؛ ساخت اول کتابخانه‌ی `ui/` (Button، Input، Modal، Badge، Dropdown) و سپس صفحات، بیشترین صرفه‌جویی را دارد.
- ‏**ریسک‌ها:** فقدان طرح موبایل و نبود حالت‌های loading، خالی و خطا در طراحی.
- ‏**ترتیب پیشنهادی پیاده‌سازی:** ۱) راه‌اندازی پروژه، فونت، RTL و CSS ← ۲) کتابخانه‌ی `ui/` و layout (هدر/فوتر/۴۰۴) ← ۳) صفحه‌ی اصلی و جستجو ← ۴) ورود (OTP) و middleware ← ۵) جزئیات تور و سبد خرید ← ۶) checkout ← ۷) پروفایل، تورهای من و تراکنش‌ها ← ۸) ریسپانسیو و حالت‌های خطا و loading.
